Axes, every column type, and the description

Three axis treatments for the histogram — 5a 5b 5c. Then 4b applied to all five column types your renderers produce. Then two answers on the description, which I did shrink and shouldn't have decided alone. Datetime numbers come from your daily_2026-08-16 report; the rest from the Titanic one.

The axis

Today's histogram prints the column name inside the chart and bare numbers on both axes — 20 40 60 along the bottom, 0 20 40 60 80 100 up the side, and nothing saying which is years and which is rows. The name is redundant once the card header carries it, and the units are the part that's actually missing. Three ways to spend those marks:

5a

Quiet

{{ l.label }}
{{ t.label }}
age in years, 25 bins · height is rows, peak 83
PRO

Two numbers instead of six on the y axis; the shape dominates. Reads well small, so the same chart works in the mobile card unchanged.

CON

You cannot read a middle bar's count — only estimate it. For a profiling report that is a real loss.

5b

Ruled, with units on the axes

ROWS
{{ l.label }}
{{ t.label }}
YEARS
PRO

Any bar's count is readable to about ±10 rows, and ROWS / YEARS answer the units question inside the chart, where the reader is looking. Units come from the dtype and the column name, so they need no new statistics.

CON

Most marks of the three. For a unitless column the x label has nothing honest to say and has to be omitted, so the renderer needs that branch.

5c

No axis, annotated instead

{{ m.label }}
0.42 years peak 83 rows at 26–29 80 years
PRO

Quartile marks put the median and IQR on the chart, so the shape and the summary statistics stop being two separate things to reconcile.

CON

No counts at all, and the annotations collide on skewed columns like Fare, where Q1, median and Q3 all land in the first fifth of the axis.

The description

You're right — I cut it to a one-line link without asking. It's the only human writing in the whole report, so it deserves a decision rather than a default. Today it is a collapsed card at the bottom of Summary that says "Description ▸" and, when opened, "Click to add description…". Two ways to treat it:

5e

An abstract, above the numbers

EDA Report

Generated 2026-03-01 00:15:48 · Shape 891 rows × 12 columns

Kaggle's Titanic training split, pulled 2026-02-28. Cabin is mostly empty and should not be used as a feature without imputation. Age is missing for a fifth of passengers.

edit note
Summary
When nobody has written one Add a note — what this data is, where it came from, what to watch for.
PRO

A warning like "Cabin is mostly empty" is read before the reader draws conclusions, not after. When you send the file to someone, the first thing they see is a person explaining the data rather than a wall of statistics.

CON

Reports generated in a loop will never have one, so most readers meet an empty invitation above the data. It also pushes the first number about 90px down the page.

5f

A margin note, where the numbers are

Summary
{{ k.label }} {{ k.value }}
Note

Kaggle's Titanic training split, pulled 2026-02-28. Cabin is mostly empty and should not be used as a feature without imputation.

edit
When empty + add a note
PRO

Costs one 44px line when empty, so an automated report is not disfigured by an invitation nobody will accept. The olive rule marks it as the one human voice on the page without a card around it.

CON

Sits below the statistics, so a caveat written there can be missed by someone who already scrolled past to the variables.

What I'd do

Both, driven by whether the field is empty. No note: the single 44px line from 5f, so a generated report stays clean. A note exists: promote it to the abstract position in 5e, because someone bothered to write it and it should be read first. One condition in the template, and the empty case stops costing anything.
