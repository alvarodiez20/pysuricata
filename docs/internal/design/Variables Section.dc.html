Making the flags mean something

You asked how a reader is meant to know what "5 of 12 columns need a look" means, and what each flagged thing means. They cannot, and the reason is structural rather than cosmetic: the block reports measurements and the reader needs consequences. Below is what is wrong with it, then two ways to close that gap, then the pagination problem sitting underneath.

Closing the gap
15a

Group by what to do, not by which column

A list of columns with flags asks the reader to work out the consequence for each one. A list of consequences with columns under them has already done that work. Same five columns, same chips, reordered so the heading of each group is the thing a reader would have had to conclude — and each chip now carries its threshold on its face instead of in a tooltip.

PRO

The reader learns what to do without knowing what kurtosis is. 33.20 kurtosis · limit 10 is judgeable where 33.20 heavy-tailed is not, and the threshold is already in data-threshold — it was only ever hidden in a title, which is invisible on a phone and absent from a PDF. Bordered chips also fix the run-together, and the four group headings replace the vague "need a look".

CON

The group headings are advice, and a profiler giving modelling advice is a step beyond reporting facts — "drop or impute before modelling" is wrong for someone who is not modelling. It also needs a flag-to-group mapping maintained by hand, and a column with flags in three groups appears three times, which the current one-row-per-column form avoids.

15b

A flag reference, once per report

The conservative half of 15a: keep the block one row per column, and make the vocabulary decodable by writing it down once. Four columns — the flag, what was measured, the threshold that fired it, and what it means for the data. It is the tooltip content, printed, plus the sentence the tooltip never had.

PRO

Says nothing the profiler cannot stand behind — measured, threshold, implication, no advice. Built from flags actually raised, so it is four rows on Titanic and empty on a clean frame, and it costs nothing to maintain beyond the string that already exists next to each threshold in the code.

CON

A reference is a thing you have to go and read, and the reader who most needs it is the one least likely to. It also leaves the attention list itself unchanged, so "need a look" still does not say look for what.

Underneath · the toolbar and the pagination
Fix before any visual work pagination.js:163

Pagination hides off-page cards with card.style.display = 'none'. On a 60-column frame that removes 50 cards from the document, and four things break at once.

{{ b.what }} {{ b.body }}

The print case is the worst because it is silent. Someone exports a 60-column profile to PDF, gets ten columns, and has nothing telling them fifty are absent — the page control does not print either. The fix is to collapse rather than hide: every column keeps its header row in the document, and only the body folds. Find works, anchors land, print shows all sixty.

15c

The toolbar says what it is showing

Three mechanisms decide which cards you see — search, type filter, page — and their combined state is reported as Showing 1-10 of 12. Filter to datetime on Titanic and you get an empty grid with no explanation, because the tab renders whether or not the type exists.

PRO

A tab with a count tells you what filtering will do before you click, and a type with no columns gets no tab — the same rule as the zero-width donut segment and the one-option Top-N chooser. Most missing first is the sort a profiling report is actually read in, and the attention block already ranks that way internally.

CON

Sort is new interactive state on top of three existing mechanisms, and reordering cards means the report no longer matches the dataframe's own column order — which is the order someone reading alongside their code expects.

PRO

A collapsed row is more useful than a hidden one and more useful than a page number: fifty rows of name, type and flags is a readable index of the rest of the frame, and it is the same 44px row shape as the sample table and the missing list.

CON

Fifty rows is 2,200px of scroll where a page control was 40px, so the page gets longer even though it gets more honest. The cards' charts also stay in the file either way, so this changes nothing about report size — the 250 KB problem is elsewhere.

What I'd do

Take 15b's reference and put 15a's chips in the existing block — value, label and threshold on the face, bordered so they stop running together. That fixes the "what does this mean" gap without the profiler giving modelling advice, and it is mostly a change to annotate_flags plus CSS.

Then the display: none fix, which is correctness. Then 15c. I would hold 15a's grouping until you decide whether pysuricata should recommend actions at all — it is the highest-value option here and the only one that makes a claim beyond the data.

Separately, and regardless: look at the 20% cliff. A column missing 19.9% of its values not appearing in the attention block is a threshold artefact, not a judgement. Either the missing chip is actionable at warn too, or the block gains a quieter tier for things just under a limit.
